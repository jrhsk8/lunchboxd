# App shell — pages, routing, design language

The single-page structure, how routing works, and the visual idioms every new surface should reuse. Sourced from `src/`, authoritative as of 2026-07-23.

## Pages and routing

The app is one React SPA with **hash routing** (`src/ui.tsx` `useRoute`):

- `#/` (or no hash) — home: hero, rank-a-food / sign-in panel, and the categories/activity/**eaters** tabs.
- `#/u/<handle>` — a profile page ([Profile.tsx](../../src/Profile.tsx)): stats tiles + full ranking history. Handles are percent-encoded in hrefs (`profileHref`); malformed encodings fall back to home.
- `#/c/<name>` — a category page (`CategoryPage` in App.tsx): name, average, everyone's rankings, and the admin tools for admins. Looked up by name through `categories`' citext unique, so the URL is case-insensitive; `categoryHref` percent-encodes. Category names link here from every feed via `CategoryLink`, plus a "Category page →" link in the expanded board panel.
- `#/terms` — the terms of service (`Terms` in App.tsx). A route, not a modal: it's the page stating the privacy position, so it has to be linkable. Adding a route means adding a case to `useRoute`'s union, the `routeKey` scroll-reset **and** the `document.title` effect in `Site`.
- `#/notifications` — your notifications (`NotificationsPage` in App.tsx), reached from the bell in the header. **The only private page on the site**: everything else renders the same for everybody, and this renders nothing at all when signed out. Chosen over a header dropdown and a passive line on your own profile — owner-ruled 2026-07-25 (#46), knowing a page costs a table (data-model.md § Notifications) where a badge alone would have needed one timestamp. What it buys is a URL and somewhere for follows (#36) and reports (#37) to land later.
- `#/t/<hashtag>` — a hashtag page (`TagPage` in App.tsx): every review containing `#hashtag`, newest first. Reviews render through `ReviewText` (ui.tsx), which linkifies `#hashtag` tokens via `tagHref`. Matching is case-insensitive and word-bounded — a DB `ilike '%#tag%'` prefilter refined by a client-side regex, so `#tag` doesn't match `#tagged` (`useTagReviews` in data.ts). Hashtags are purely a render/route convention: no schema change, reviews stay plain text.

**Per-route `document.title` is set by an effect in `Site`**, keyed on the route. Link previews are a separate matter the hash router can't solve — a crawler never receives the fragment, so `#/c/pizza` cannot carry its own `og:image`. The `og:*` tags in `index.html` are therefore static and site-wide; making them per-URL would mean real paths plus prerendering.

Hash routing is a deliberate choice, not a shortcut: the site is a static build on Cloudflare Pages (`lunchboxd.live`) with no SPA-fallback rewrites configured, so path routing would 404 on deep links. Hashes also can't collide with Supabase magic-link fragments (`#access_token=…`), which supabase-js consumes and clears on load. The header/footer stay mounted across routes; only the body swaps (`Site` in App.tsx).

## Component map

- `App.tsx` — `Site` (shell + route dispatch), `RankForm` (one datalist-backed category field — type-ahead over existing names, and typing a new one invents it; there is no separate "new category" mode), `CategoryBoard`/`CategoryDetail`, `CategoryPage`, `TagPage`, `RankingRows` (the row list shared by panel and page), `CategoryTools` + `categoryToolsFor` + `DeleteCategoryButton` (admin rename / merge-into / delete, or the inventor's delete alone, in both the panel and the page), `ActivityFeed`, `Terms`, `WhatsNew`.
  - `categoryToolsFor` decides which set a viewer gets and is the client half of `delete_category`'s rule — call it, don't re-derive it, and note that both call sites need it: the page also uses it to decide whether to draw the panel the tools sit in.
- **`EatersTab`** (App.tsx) — the third board tab: everyone who has ever ranked, drawn as their calling card, 2 across on desktop and 1 on a phone. **A tab, not a route** — owner-ruled 2026-07-25 (#44), knowing the cost: it can't be linked to, and a card list is the kind of thing people link. It's the card's second home, and the only place the three stats somebody chose about themselves are visible to anyone else — which is why it's cards rather than the denser compact rows the board idiom would suggest. Four sort settings (Recent — the default — Rankings, Likes, A–Z) in a **radiogroup**, not a tablist, with short labels so all four fit at 320px. 24 at a time behind a "Show more (N to go)"; the sort and the paging both happen in the database (§ `eaters` view in data-model.md), so the cap is a real `range` rather than a slice of everybody. Changing the sort resets the depth: a new ordering is a new list.
- `Profile.tsx` — `ProfilePage` (stats + history; own-view gets edit controls), `TopFour`/`TopCard` (the pinned four, above the stat tiles; the empty dashed spots appear on your own profile only, where they're the instruction).
- `auth.tsx` — `useAuth`, `SignInCard` (guest-first), `KeepAccount`.
- `Stars.tsx` — `Stars` (fractional display), `StarInput` (half-star hit zones).
- `ui.tsx` — shared: the `panel`/`kicker`/`btnPrimary`/`input`/`label` class strings, `scoreTone`, `useRoute` + the `*Href` builders, `UserLink`/`CategoryLink`, `ReviewText` (hashtag linkifier), `ReviewQuote` (the clamped quote + "more" expander), `Tag`/`profileTags`, `Heart`, `LoadError`, and **`RankingRow`**.
  - **`RankingRow` is the one row implementation.** It was three near-identical ~40-line blocks (board panel, activity feed, profile page) differing only in their headline, so every mobile fix had to be applied three times by hand. It takes a `headline` slot, a container `className`, `controls` (`'none'` for the activity feed, which doesn't reserve the owner column; `'owner'` elsewhere) and `pin` (the top-four control, own profile only — see data-model.md § The top four). Delete confirmation, the inline editor, the review expander and the pin all live inside it — add row behaviour here, not at a call site.
  - **The like (`LikeControl`) leads the row's second line, in a fixed 74px column**, with the review quote beside it — owner-ruled 2026-07-25 (#45). Three placements were prototyped: a pill on the meta line (fits, but a seventh control on the tightest line on the site), an action row of its own under the content (cost the list ~40% of its height at twelve rows), and this. The fixed column is what makes it a column: the mark sits at the same x on every row, review or not, and so does every review beside it. The cost is 86px of review width on a phone, which turns some one-line quotes into two — accepted for the alignment. **It is not a heart and not gold**: the row already carries the author's gold heart, and a second heart in clay read as a bug rather than a distinction.
  - `LikeControl` reads `LikesContext` (provided once in `Site` from `useMyLikes`), not props, because every row on every surface needs the same two answers. Its `viewer` decides what the UI _offers_ — `'out'`, `'guest'`, `'email'` — and the guest case is an invitation to keep the account, not a refusal. The check leans on the JWT's `is_anonymous`, which is stale in the safe direction only: never invert it to _grant_ liking, since the DB's `caller_has_email()` is the real gate (data-model.md).
  - The pin (`TopPin`) keeps its filled mark visible rather than borrowing `ownerControl`'s hover-reveal: the diamond is **state**, not just a control, and a mark that only appears on hover says nothing on a touch screen. The two share `controlBase` instead of one class string carrying both `sm:opacity-0` and `sm:opacity-100`, where which wins depends on Tailwind's emit order rather than on anything readable.
  - `NotificationBell` is a **link**, not a dropdown trigger — the notifications are a page, and a header control that both opens a panel and navigates is two affordances in one 28px target. The bell glyph is an inline SVG for the same reason the brand mark is: the site has one typeface and no icon set, and the nearest characters render as emoji on some platforms. It draws only for a signed-in viewer.
  - `btnPrimary`/`input`/`label` were duplicated in App.tsx and auth.tsx, with auth's copy carrying a drifted extra `w-full`. auth.tsx now composes `w-full` on top. Don't re-derive these.
- `text.ts` — the pure helpers (`timeAgo`, `HASHTAG_RE`, `hashtagsIn`, `TOP_SLOTS`/`nextTopSlot`), split out of ui.tsx so `text.test.ts` can import them without pulling in React or the Supabase client (which builds a realtime client at module load and needs a WebSocket). New pure logic worth testing goes here.
- `ErrorBoundary.tsx` — wraps `<App />` in main.tsx. Logs to console only: the Terms' no-analytics promise rules out a third-party reporter without a ruling.
- `data.ts` — all Supabase reads/writes; components never touch the client directly except auth flows.
- `releases.ts` — the version history: a newest-first list of releases, and `version` (= `releases[0].version`). **Nothing in the UI reads it** — the footer's version button and its What's-new dialog were removed on 2026-07-24 (decisions.md). Shipping a release still means adding an entry at the top **and** bumping `package.json` to match; neither derives from the other. If anything ever renders `version` inside `Site` again, **import it aliased** (`version as siteVersion`): `version` there is `useBoard`'s refresh counter and shadows the unaliased import, silently showing the poll count instead of the release number.

## Design language

Lifted from Maxout's v2 editorial dark skin; tokens live in `src/index.css` `@theme` (Tailwind v4).

- **Brand:** the lunchbox-with-star mark. Assets and the lockup/sizing/don'ts spec live in `public/brand/` (README.md there is authoritative). The header renders the on-dark mark inline in App.tsx; the favicon is the clay-tile version.

- **Ground:** warm near-black (`bg`), panels on `panel` with `--radius-card` and the hard drop shadow. Panels use the shared `panel` class string from ui.tsx — don't re-derive it.
- **Accent:** clay (`clay`/`clay-hover`) for kickers, links, and primary buttons; gold for stars and hearts; `good`/`bad` for score tones via `scoreTone` (≥4 good, <2.5 bad).
- **Type:** single typeface (Schibsted Grotesk). Section headers are uppercase tracking-wide "kickers" (the shared `kicker` class). Numbers are `tabular-nums`.
- **Interactive idioms:** usernames render through `UserLink` (clay hover) everywhere they appear; owner-only controls (delete, heart toggle) reveal on row hover; empty states are a panel with a bold one-liner plus a playful sub-line.
- **Username tags:** maxout's player-badge pattern — one hue drives text, dot, border, and fill of a small chip (`Tag` in ui.tsx). Roster: `admin` (red, granted), `supporter` (teal, granted — teal because the obvious gold is the heart's colour and a warm chip beside a handle reads as a love mark), `peloton` (blue, self-picked), `zwift` (murky chartreuse, self-picked — ugly on purpose, owner-ruled), `runner` (violet, self-picked). The two granted chips come from their own columns and render first; flair is either/or — one self-tag at most, DB-enforced (`profiles_tags_single`), and the picker swaps rather than stacks — so a supporter still wears their flair beside the badge. `profileTags` builds the list and deliberately filters the self-writable `tags` column against `SELF_TAGS`, not against every known chip, so a granted badge can never be rendered out of user-supplied data. Tags ride along wherever `UserLink` gets a `meta` prop; the flair picker lives on your own profile page.

- **Mobile:** the page is a single centered column that already reflows (stat tiles are `grid-cols-2 sm:grid-cols-4`, etc.). The header hides the rankings/categories count below `sm`. Five idioms carry the phone layout, all of them `sm:`-gated so desktop stays pixel-identical (verify that claim by screenshot-diffing 1280px before/after any of these):

  - **Rows stack, then collapse.** The ranking row and the category board row both put their content on line one and their meta (time/stars/score/heart/delete, or stars/score/caret) on line two, using `flex-wrap` + a `w-full ... sm:contents` wrapper — at `sm+` the wrapper vanishes and the children rejoin the single desktop line. Without this the board row gave each category name ~25px at 320px, i.e. one letter and an ellipsis.
  - **Feed headlines wrap on phones, truncate on desktop** (`block sm:truncate`). One ellipsised line always lost its tail, and the tail is the category — the link out of the feed.
  - **Reviews clamp to three lines on phones** (the shared `reviewLine` in ui.tsx), one ellipsised line at `sm+`, with a **"more" expander** when the text actually overflows (`ReviewQuote` measures rather than guessing from length). The clamp used to be the end of it, with the full text only in a `title` tooltip that a touch device never shows — so a 2000-character field was unreadable past ~200 characters on a phone.
  - **Anything user-named needs `break-words`** (`break-all` inside a flex container, where `overflow-wrap` doesn't shrink min-content): hashtags have no length cap, category names run to 60 chars and handles to 24, any of which can arrive as one unbroken token and sail off the right edge. Header columns that hold such text need `min-w-0`, or the column sizes to its max-content and drags the page with it.
  - **Owner-only hover controls must be visible without hover** (`opacity-100 sm:opacity-0 sm:group-hover:opacity-100`), or the feature is unreachable on touch. Delete sits beside the heart under this rule — two adjacent small targets, one destructive — which is why it confirms.
  - **The star input scales up below `sm`** (44px vs 30px). Ten hit zones across five 30px stars is ~16px each, well under the ~44px touch guideline, on the primary action of the whole site.

## Accessibility idioms

- **Scores** render through `Stars`, which is `role="img"` with an `aria-label`. The role is load-bearing: `aria-label` on a bare span isn't reliably exposed, and both glyph runs are `aria-hidden`, so the label is the only announced text.
- **`StarInput` is a radiogroup with a roving tabindex** — one tab stop, Left/Right by a half star, Home/End for the ends — and its focus ring goes on the wrapper via `has-[:focus-visible]`, because the hit zones are `opacity-0` and hide the default outline with everything else.
- **The board has three tabs, and the arrow keys know it.** `TABS` in App.tsx is the single source of tab order; the keydown handler steps through it modulo its length rather than flipping between two names, which is what it did when there were two. Adding a fourth means adding it to that array and nothing else.
- **The board's categories/activity/eaters switch is a real tablist** (`role="tablist"`/`tab`/`tabpanel`, `aria-selected`, arrow keys). The Top-rated/A–Z control next to it is a **radiogroup**, not a tablist — it picks an ordering rather than switching panels, and `role="tab"` without a tabpanel would announce something untrue.
- Toggles that aren't either of those use `aria-pressed` (`Heart`, "Loved it", `TagPicker`).

  Within the ranking row's name line the **username gets display priority** (`shrink-0`, never truncates), and the food wraps onto its own line rather than shortening — owner-ruled 2026-07-24, reversing the earlier "shorten food". Nothing on a phone is ellipsised that could wrap instead.

- **Shell width:** `max-w-[1320px]`, not the original 1140. The feed headline ("X ranked FOOD in CATEGORY") is the widest thing on the site and the category sits at the end, so it was what got cut; at 1140 the feed was pinned to 676px at every screen width and a third of activity rows truncated. Changing this width changes how much of a headline survives on desktop — measure the truncated-row count before and after, don't eyeball it.
